    UT2 · Programación web en servidor con PHP¶

    Esta página reúne toda la teoría de la UT2 en un único tema, con sus apartados y subapartados en la tabla de contenidos.

    UT2 · 1. PHP, variables y generación de HTML¶

    Dónde se ejecuta cada cosa¶

    PHP se ejecuta en el servidor. El resultado puede ser HTML, JSON o texto. El navegador no ejecuta el PHP original. Abrir un .php como archivo local no equivale a solicitarlo a un servidor PHP.

    Para estos ejemplos puedes utilizar la carpeta public del laboratorio de UT1. Si tienes instalado el intérprete PHP, también puedes probar solo PHP con php -S 127.0.0.1:8093 -t public. Ese servidor es para desarrollo local y no reproduce el stack completo de Nginx y MariaDB.

    Las reglas básicas¶

    Las variables comienzan por $ y distinguen mayúsculas. = asigna; === compara valor y tipo. Las instrucciones suelen acabar en ;. El punto . concatena texto y echo escribe en la respuesta. <?= expresion ?> equivale a imprimir esa expresión.

    Tipo Ejemplo Para qué sirve
    int 24 Recuento entero
    float 2.75 Cantidad decimal
    string 'Sala violeta' Texto
    bool true Una condición
    array ['A', 'B'] Una colección
    null null Ausencia de valor

    Las comillas dobles pueden interpolar variables; las simples conservan el texto literal. // y /* ... */ son comentarios PHP. Un comentario HTML puede llegar al navegador; un comentario PHP no forma parte de la respuesta.

    Qué hace PHP antes de que el navegador reciba la página¶

    Un archivo PHP puede contener instrucciones del servidor y texto que formará parte de la respuesta. Cuando llega una petición, el intérprete ejecuta las instrucciones y produce una salida. El navegador recibe esa salida, no el programa que la generó.

    Esto permite que dos visitas al mismo archivo reciban contenidos distintos: el programa puede utilizar datos enviados, resultados de una consulta o el estado de una sesión. Para empezar, usamos valores fijados dentro del código y así podemos seguir el cálculo sin añadir todavía formularios.

    La apertura habitual es <?php. Dentro de ese bloque escribes instrucciones PHP, que suelen terminar con punto y coma. Al cerrar con ?>, vuelves a texto de salida, normalmente HTML. La forma <?= $valor ?> imprime directamente una expresión dentro de esa salida.

    Leer una asignación de derecha a izquierda¶

    En $libres = $capacidad - $reservas;, primero se leen los valores de la derecha, se calcula la resta y después se guarda el resultado bajo el nombre de la izquierda. El signo = no pregunta si ambos lados son iguales.

    Si cambias $reservas más tarde, $libres no se recalcula por sí solo. Una variable que contiene el resultado no conserva una fórmula viva. Tendrás que ejecutar de nuevo la operación cuando corresponda. Esta idea ayuda a seguir programas donde las cantidades se actualizan por pasos.

    <?php
$capacidad = 10;
$reservas = 3;
$libres = $capacidad - $reservas;
$reservas = 5;
echo $libres . "\n";
$libres = $capacidad - $reservas;
echo $libres . "\n";

    Primero aparece 7 y después 5. La segunda asignación a $reservas no modifica la resta anterior; la nueva resta sí obtiene el valor actualizado.

    Texto, números y booleanos tienen papeles distintos¶

    '18' es texto y 18 es un entero. Pueden representar una información parecida para una persona, pero no son el mismo tipo. Una entrada HTTP llega normalmente como texto y debe validarse antes de usarse como cantidad.

    Una comparación como $libres === 0 produce true o false. Ese resultado puede utilizarse después en una decisión. No necesitas escribir el texto 'true': sería una cadena de cuatro letras, no el valor lógico.

    Conocer el tipo evita interpretar una salida engañosa. var_dump resulta útil porque muestra valor y tipo; imprimir solo un booleano con echo puede ser poco claro, ya que su conversión a texto no presenta necesariamente las palabras que esperas.

    Concatenación e interpolación¶

    La concatenación une textos con .. Las comillas dobles permiten interpolar una variable sencilla; las simples conservan el texto literal. Ambas formas son válidas si sabes qué resultado construyen.

    <?php
$sala = 'Azul';
echo 'Sala: ' . $sala . "\n";
echo "Sala: $sala\n";
echo 'Sala: $sala' . "\n";

    Las dos primeras líneas muestran Sala: Azul; la tercera muestra literalmente Sala: $sala. El salto \n funciona aquí dentro de comillas dobles. En una página HTML normal, un salto del código fuente no obliga al navegador a dibujar otra línea: necesitas una estructura HTML adecuada.

    Separar el cálculo de la presentación¶

    Organiza primero los datos y después el HTML que los muestra. De ese modo puedes comprobar una resta o una condición sin mezclarla con etiquetas y estilos. No hace falta crear una arquitectura complicada: basta con que el lector sepa dónde se preparan los valores y dónde se representan.

    Cuando un valor contiene texto externo, escápalo al insertarlo en HTML. La razón no es que PHP no sepa imprimirlo, sino que el navegador podría interpretarlo como marcado. El ejemplo del taller muestra tanto el cálculo de plazas como la presentación segura del nombre.

    Problema explicado paso a paso: plazas de un taller de cerámica¶

    Objetivo: mostrar las plazas disponibles. No hay formulario ni datos de clase: los valores están fijados para seguir el cálculo.

    Guarda taller.php:

    <?php
$capacidad = 18;
$reservas = 11;
$libres = $capacidad - $reservas;
$nombre = 'Cerámica & color';
$completo = $libres === 0;
?>
<h1><?= htmlspecialchars($nombre, ENT_QUOTES, 'UTF-8') ?></h1>
<p>Plazas libres: <?= $libres ?></p>
<p><?= $completo ? 'Sin plazas' : 'Inscripción abierta' ?></p>

    Razonamiento paso a paso¶

    1. PHP asocia 18 y 11 a dos variables enteras.
    2. Resta las reservas de la capacidad: 18 - 11 = 7.
    3. La comparación 7 === 0 es falsa; $completo vale false.
    4. El ternario condicion ? valor_si : valor_no elige el texto «Inscripción abierta».
    5. htmlspecialchars transforma los caracteres especiales para insertar texto en HTML. El ampersand se codifica en el código fuente y el navegador muestra &.

    Resultado visible: «Cerámica & color», «Plazas libres: 7» e «Inscripción abierta». Si reservas 18 plazas, verás 0 y «Sin plazas». Si pones 20 reservas, aparece un número negativo: el programa necesita una regla de validación; la resta, por sí sola, no garantiza datos coherentes.

    Operadores que utilizarás¶

    +, -, *, / y % calculan. &&, || y ! combinan o niegan condiciones. ?? aporta un valor alternativo cuando un dato no existe o es null, como en $_GET['sala'] ?? ''. No valida que el dato sea correcto.

    Un array indexado utiliza posiciones: $salas = ['Azul', 'Verde']; y $salas[0] devuelve Azul. Un array asociativo utiliza claves: $sala = ['nombre' => 'Azul', 'capacidad' => 18];. Accedes con $sala['capacidad']. Si la clave no existe, compruébala o utiliza ??.

    Error Causa y solución
    Undefined variable Revisa el nombre y la asignación antes de usarla.
    Parse error Mira ;, comillas y llaves, también en la línea anterior.
    Se muestra código PHP Abres el archivo directamente o el servidor no lo procesa.
    El texto del usuario se convierte en HTML Escápalo en el punto donde generas HTML.

    Texto, tipos y operaciones que conviene distinguir¶

    Los apuntes anteriores separaban bien la operación que calcula de la que presenta el resultado. En PHP, . concatena texto y + suma: no utilices uno esperando el comportamiento del otro. strlen cuenta bytes; para contar caracteres de texto multibyte puedes utilizar mb_strlen, si la extensión correspondiente está disponible.

    <?php
$texto = '  sala azul  ';
$limpio = trim($texto);
echo strtoupper($limpio) . "\n";
echo str_replace('azul', 'verde', $limpio) . "\n";

    Salida esperada: SALA AZUL y sala verde. trim limpia los extremos, no los espacios interiores. strtoupper es suficiente para este texto ASCII; el tratamiento completo de mayúsculas Unicode requiere herramientas multibyte apropiadas.

    Diagnóstico de tipos¶

    var_dump($valor) muestra tipo y contenido. Esto ayuda a explicar por qué 3 === '3' es falso: uno es entero y otro es texto. No conviertas entradas a ciegas para hacer desaparecer el error; define primero qué representación admite el programa y valida antes del cálculo.

    Ejercicios para practicar¶

    Intenta resolverlos antes de abrir la solución. Puedes consultar la teoría; después repite alguno sin mirar para comprobar qué recuerdas. Las pistas y soluciones están cerradas para que elijas cuándo verlas.

    1. Calcula el material que falta¶

    Guarda 30 como cantidad necesaria de hojas y 22 como cantidad disponible. Escribe un programa PHP que calcule lo que falta y muestre una frase. Calcula primero el número y construye después el mensaje.

    Pista

    Utiliza una resta y concatena el resultado con texto.

    Solución paso a paso 
    <?php
$necesarias = 30;
$disponibles = 22;
$faltan = $necesarias - $disponibles;
echo 'Faltan ' . $faltan . " hojas\n";
    1. Restamos las disponibles a las necesarias.
    2. Guardamos 8 en $faltan.
    3. Mostramos Faltan 8 hojas. El texto no se suma: se concatena con ..

    2. Comprueba cuándo se calcula un valor¶

    Sin ejecutarlo primero, predice las dos líneas de este programa. Después compruébalo y explica por qué $b no cambia al asignar 10 a $a.

    <?php
$a = 6;
$b = $a + 1;
$a = 10;
echo $b . "\n";
$b = $a + 1;
echo $b . "\n";
    Pista

    Una asignación guarda el resultado de ese momento, no una fórmula que se actualice sola.

    Solución paso a paso

    Las líneas son 7 y 11.

    1. La primera asignación a $b calcula 6 + 1.
    2. Cambiar $a a 10 no vuelve a ejecutar esa suma.
    3. La segunda asignación a $b sí calcula con el nuevo valor: 10 + 1.

    Para comprobarlo, guarda el programa en un archivo y ejecútalo con PHP.

    3. Une texto sin ejecutar etiquetas¶

    La variable $titulo contiene <em>Rutas del barrio</em>. Genera un párrafo HTML que muestre ese contenido como texto, sin que se convierta en cursiva. No sustituyas manualmente cada carácter.

    Pista

    La transformación corresponde al momento de presentar el texto en HTML.

    Solución paso a paso 
    <?php
$titulo = '<em>Rutas del barrio</em>';
echo '<p>' . htmlspecialchars($titulo, ENT_QUOTES, 'UTF-8') . '</p>';
    1. Las etiquetas del párrafo son parte de nuestra presentación.
    2. El contenido de $titulo se escapa antes de insertarlo.
    3. El navegador muestra literalmente <em>Rutas del barrio</em> dentro del párrafo.

    Palabras clave de este tema¶

    Término Significado en este tema
    Variable y tipo de dato Nombre asociado a un valor y categoría que determina qué operaciones admite.
    Cadena y booleano Texto y valor lógico verdadero/falso, respectivamente.
    Sintaxis Reglas que permiten interpretar instrucciones de un lenguaje.
    Escape de HTML Transformación de texto para que no se interprete como marcado en el contexto de salida.

    Para repasar

    Primero se calculan los datos; después se genera la respuesta. Validar datos y escapar HTML son operaciones diferentes.

    UT2 · 2. Decisiones, bucles, arrays y funciones¶

    Elige la estructura según el problema¶

    Utiliza if/elseif/else cuando importen condiciones o intervalos; switch cuando compares opciones concretas. Un for sirve para una repetición con contador; while, para repetir mientras se cumple una condición; foreach, para recorrer los elementos de un array.

    No escribas un bucle por costumbre. Pregúntate qué cambia en cada vuelta, cuándo termina y qué resultado debes acumular.

    Pensar una decisión antes de elegir la sintaxis¶

    Un condicional responde a una pregunta. Antes de escribir if, exprésala con palabras: «si no quedan paquetes, termina» o «si la opción es audio, muestra escuchar». Después elige qué dato debe compararse y qué valores produce cada camino.

    if sirve para una pregunta. elseif permite comprobar otra cuando la anterior fue falsa. else recoge los casos restantes. No se ejecutan todas las ramas de una cadena, sino la primera que corresponde. Si necesitas ejecutar varias comprobaciones independientes, utiliza varios if y explica por qué no se excluyen entre sí.

    switch puede resultar más cómodo al comparar una misma opción con varios valores concretos. Cada break evita continuar dentro del siguiente caso. No lo introduzcas solo para hacer más corto el programa: primero debe estar claro qué caso representa cada valor.

    Un array reúne datos que vas a tratar de la misma manera¶

    En lugar de crear $sala1, $sala2 y $sala3, puedes reunir los nombres en un array y recorrerlo. En un array indexado accedes por posición; en uno asociativo, por una clave que expresa el significado del dato.

    <?php
$salas = ['Azul', 'Gris'];
$aforo = ['Azul' => 18, 'Gris' => 12];
foreach ($salas as $sala) {
    echo $sala . ': ' . $aforo[$sala] . " plazas\n";
}

    La salida muestra Azul: 18 plazas y Gris: 12 plazas. La variable $sala toma un nombre en cada vuelta. Ese nombre permite consultar su cantidad en el segundo array. Este ejemplo presupone que ambas colecciones contienen las claves correspondientes; si los datos fueran externos habría que comprobarlo.

    Qué se repite en un bucle¶

    Un bucle ejecuta un bloque varias veces. La parte que cambia puede ser el elemento que recorres, un contador o una cantidad pendiente. Lo que debe conservarse entre vueltas se inicializa antes; lo que representa un cálculo nuevo se obtiene dentro.

    En el ejemplo de cajas, el total debe empezar en cero antes de foreach, porque reúne resultados de todos los lotes. El número de cajas del lote se calcula dentro, porque cambia con la cantidad de cada lote. Si inicializas ambos en el mismo lugar por costumbre, uno de ellos perderá su propósito.

    Para depurar, escribe una fila por vuelta: valor actual, condición, resultado y acumulador. Esa tabla te permite comprobar el bucle sin ejecutarlo mentalmente de golpe.

    Crear una función significa poner nombre a una tarea¶

    Una función tiene entradas, un trabajo y, si corresponde, una salida. Los parámetros son nombres que recibirán valores en cada llamada. return entrega el resultado y termina esa ejecución de la función; no imprime una respuesta para el usuario.

    <?php
function plazasLibres(int $capacidad, int $ocupadas): int
{
    return $capacidad - $ocupadas;
}
$primeraSala = plazasLibres(18, 11);
$segundaSala = plazasLibres(12, 4);
echo $primeraSala . ' / ' . $segundaSala . "\n";

    La salida es 7 / 8. No se ejecuta la resta al definir la función, sino en cada llamada. La primera utiliza 18 y 11; la segunda utiliza 12 y 4. Los nombres internos no obligan a que las variables del programa que llama tengan esos mismos nombres.

    Esta separación facilita probar: puedes llamar a la función con cantidades pequeñas y saber qué esperas. Si dentro leyera directamente un formulario, necesitarías preparar además una petición HTTP para comprobar la misma resta.

    Evitar funciones que hacen demasiadas cosas¶

    Una función que lee un formulario, valida, calcula, escribe HTML y redirige es difícil de reutilizar. Empieza por una separación sencilla: el receptor obtiene y valida; la función calcula; el HTML presenta. No hace falta convertir cada línea en otra función.

    Utiliza nombres que expliquen el propósito. plazasLibres dice más que hacerCosas. Una función que devuelve una cantidad debería entregar esa cantidad, no una frase ya decorada que después tengas que volver a interpretar.

    Problema explicado paso a paso: preparar cajas de libros¶

    Hay tres lotes de libros. Cada caja admite seis ejemplares. Queremos mostrar cuántas cajas necesita cada lote y el total de cajas; los lotes no se mezclan.

    <?php
function cajasNecesarias(int $libros, int $capacidad): int
{
    return (int) ceil($libros / $capacidad);
}

$lotes = ['Poesía' => 13, 'Teatro' => 6, 'Ensayo' => 2];
$total = 0;
foreach ($lotes as $categoria => $cantidad) {
    $cajas = cajasNecesarias($cantidad, 6);
    $total += $cajas;
    echo htmlspecialchars($categoria, ENT_QUOTES, 'UTF-8')
        . ': ' . $cajas . " cajas\n";
}
echo 'Total: ' . $total . " cajas\n";

    Puedes ejecutarlo como script con php lotes.php. En una página HTML, utiliza <pre> o elementos HTML para ver los saltos de línea.

    Teatro 6 6 / 6 = 1 1 4
    Ensayo 2 2 / 6 ≈ 0,33 1 5

    ceil redondea hacia arriba: una caja medio llena sigue siendo una caja. El casting (int) convierte el resultado a entero. return devuelve el valor a la llamada; no lo imprime. La función presupone cantidades no negativas y una capacidad positiva: valida esas condiciones si pasan a ser datos introducidos por el usuario.

    Decisiones con ejemplos pequeños¶

$pendiente = 4;

    Ejecutado en el terminal, este bloque muestra primero Hay que continuar y después Escuchar, en líneas separadas.

    break evita continuar con el siguiente caso. El switch tradicional hace comparaciones flexibles; con entradas mixtas conviene validar el tipo o utilizar comparaciones estrictas con if.

    Repetir con contador o condición¶

    <?php
for ($turno = 1; $turno <= 3; $turno++) {
    echo "Turno $turno\n";
}
$paquetes = 2;
while ($paquetes > 0) {
    echo "Quedan $paquetes\n";
    $paquetes--;

    El for muestra los turnos 1, 2 y 3. El while muestra 2 y 1, y termina cuando el contador llega a cero. Si olvidas decrementarlo, nunca llega a la condición de parada.

    Reutilizar sin perder el hilo¶

'/funciones.php'; carga un archivo necesario una vez; include genera un aviso si no puede cargarlo y puede continuar. Utiliza rutas propias del proyecto, no una ruta recibida directamente del usuario.

    UT2 · 3. Formularios: recibir, validar y conservar datos¶

    El recorrido completo¶

    HTML presenta los controles; el navegador envía los que tienen name; PHP recibe los valores en $_GET o $_POST. El servidor debe validarlos aunque el formulario utilice required, min o un desplegable: una petición se puede enviar sin utilizar esa interfaz.

    El orden que ayuda a pensar es leer → validar → calcular → mostrar. Escapar con htmlspecialchars es necesario al insertar texto en HTML, pero no comprueba que el contenido sea admisible para el problema.

    Del control HTML a una variable PHP¶

    Un formulario relaciona una interfaz con un receptor. action indica el destino y method el modo de envío. Cada control necesita un atributo name para identificar su dato; el texto de una etiqueta visible no sustituye a ese nombre.

    Imagina un control <input name="minutos">. Cuando envías 15, el servidor recibe un campo llamado minutos. En un formulario POST, PHP lo sitúa en $_POST['minutos']. No lo buscará automáticamente en una variable $minutos: debes leerlo y decidir qué hacer con él.

    id sirve para relaciones de la interfaz, como conectar un <label> con el control. name sirve para el envío. Puedes utilizar el mismo texto en ambos, pero cumplen funciones diferentes. Confundirlos hace que una entrada se vea bien y aun así no llegue con el nombre que espera el programa.

    La primera visita no es un envío vacío¶

    Al abrir la página por su URL, normalmente haces GET. Todavía no has solicitado comprobar ninguna entrada. Si intentas validar todos los campos en ese momento, mostrarás errores antes de que el usuario haya tenido oportunidad de escribir.

    Por eso el ejemplo distingue el método: primero inicializa valores para presentar el formulario y solo procesa cuando recibe POST. Después del envío puede representar errores o un resultado, conservando los datos cuando sea necesario.

    No deduzcas que hay un envío solo porque exista alguna variable. Comprobar REQUEST_METHOD expresa la intención y permite entender el flujo de la página. Los campos individuales se comprueban después, porque pueden faltar aunque el método sea POST.

    Leer, limpiar, validar y escapar son pasos diferentes¶

    Leer obtiene lo recibido. Limpiar puede quitar espacios de los extremos con trim. Validar comprueba reglas como «es un entero entre 5 y 40». Escapar prepara texto para representarlo en un contexto de salida, como HTML.

    Si alguien envía 15, puede tener sentido quitar esos espacios antes de validar. Si envía quince, quitar espacios no lo convierte en el número 15. Si envía <b>15</b>, escapar permite mostrar ese texto, pero no lo convierte en una duración válida.

    No uses una única operación para sustituir las otras. Este orden te permite explicar por qué un dato se acepta o se rechaza y evita que una presentación segura oculte una validación incompleta.

    Por qué se utiliza una lista de errores¶

    El formulario puede tener más de un problema. Un array de errores permite comprobar cada campo y añadir un mensaje para cada incumplimiento. Solo cuando la lista está vacía continúas con el cálculo o la operación.

    Los mensajes deben indicar qué corregir. «Duración fuera de rango: utiliza de 5 a 40 minutos» resulta más útil que «dato malo». Si hay dos errores, presentarlos juntos evita obligar al usuario a corregir uno y reenviar para descubrir el siguiente.

    El ejemplo conserva las entradas aceptadas como texto para volver a rellenar los controles. Al escribirlas en value, se escapan. Para un desplegable se marca la opción con selected; para una casilla se utiliza checked. No son atributos que PHP añada automáticamente por haber leído el dato.

    Cómo leer el problema del telescopio¶

    Primero sigue una visita GET: mira los valores iniciales y comprueba que todavía no hay un resultado. Después sigue un POST válido y anota qué devuelve cada llamada a campo. Finalmente, sigue un POST incorrecto y observa qué mensajes se acumulan.

    No intentes entender todo el archivo como una sola operación. Separa su parte de procesamiento y su parte de presentación. Busca después dónde se conectan: las variables que prepara la primera aparecen en los controles y en los mensajes que construye la segunda.

    Esta lectura sirve durante el examen y mientras haces otro formulario: identificas el mismo recorrido y adaptas sus reglas, en lugar de copiar campos que no pertenecen a tu enunciado.

    Problema explicado paso a paso: solicitar tiempo de un telescopio¶

    Solicitar un turno de observación de 5 a 40 minutos. Hay que elegir telescopio y aceptar la norma de dejarlo recogido. El formulario conserva los datos si hay un error. No calcula presupuestos ni resuelve la práctica de contratación de clase.

    Guarda este archivo como turno.php en el servidor PHP:

    <?php
function h(string $texto): string {
    return htmlspecialchars($texto, ENT_QUOTES, 'UTF-8');
}
function campo(string $nombre): string {
    $valor = $_POST[$nombre] ?? '';
    return is_string($valor) ? trim($valor) : '';
}
$errores = [];
$equipo = '';
$minutosTexto = '';
$aceptado = false;
$enviado = $_SERVER['REQUEST_METHOD'] === 'POST';
if ($enviado) {
    $equipo = campo('equipo');
    $minutosTexto = campo('minutos');
    $aceptado = campo('recoger') === 'si';
    $minutos = filter_var($minutosTexto, FILTER_VALIDATE_INT);
    if (!in_array($equipo, ['refractor', 'reflector'], true)) {
        $errores[] = 'Elige uno de los dos telescopios.';
    }
    if ($minutos === false || $minutos < 5 || $minutos > 40) {
        $errores[] = 'La duración debe ser un entero de 5 a 40.';
    }
    if (!$aceptado) {
        $errores[] = 'Debes aceptar dejar el material recogido.';
    }
}
?>
<!doctype html>
<html lang="es">
<meta charset="utf-8">
<title>Turno del telescopio</title>
<h1>Turno de observación</h1>
<?php foreach ($errores as $error): ?>
<p><?= h($error) ?></p>
<?php endforeach; ?>
<form action="turno.php" method="post">
    <label>Telescopio
        <select name="equipo">
            <option value="">Elige uno</option>
            <option value="refractor" <?= $equipo === 'refractor' ? 'selected' : '' ?>>Refractor</option>
            <option value="reflector" <?= $equipo === 'reflector' ? 'selected' : '' ?>>Reflector</option>
        </select>
    </label>

        <input name="minutos" type="number" min="5" max="40"
               required value="<?= h($minutosTexto) ?>">
    </label>
    <label>
        <input type="checkbox" name="recoger" value="si"
               <?= $aceptado ? 'checked' : '' ?>>Dejaré el material recogido
    </label>
    <button>Comprobar turno</button>
</form>
<?php if ($enviado && !$errores): ?>
<p>Solicitud válida: <?= h($equipo) ?> durante <?= $minutos ?> minutos.</p>
<?php endif; ?>
</html>

    ¿Por qué está escrito así?¶

    1. En GET se muestran campos vacíos y ningún error: todavía no se ha enviado nada.
    2. En POST, campo() proporciona texto o una cadena vacía. También rechaza un array inesperado, porque los datos HTTP no son fiables.
    3. El array de valores permitidos impide inventar otro telescopio modificando la petición.
    4. FILTER_VALIDATE_INT devuelve false si no puede validar el entero. No uses if (!$minutos) como sustituto general: confunde cero con fallo.
    5. Un checkbox desmarcado no envía el campo. Aquí se comprueba el valor admitido; isset($_POST['recoger']) serviría para comprobar solo su presencia.
    6. La misma variable rellena el formulario y el mensaje: los datos no se pierden cuando falla otra condición.

    XSS: validar no sustituye escapar¶

    <?php
$nota = '<b>Revisar vitrina</b>';
echo htmlspecialchars($nota, ENT_QUOTES, 'UTF-8');

    La respuesta contiene &lt;b&gt;Revisar vitrina&lt;/b&gt;; el navegador muestra las etiquetas como texto. Así no interpretas la nota como marcado HTML. Este escape sirve para texto en HTML y atributos entrecomillados; otros contextos, como JavaScript o una URL, requieren su tratamiento correspondiente.

    Guarda el dato con su significado original y escápalo al presentarlo. Escapar al guardar y volver a escapar al mostrar puede producir entidades duplicadas. La inyección SQL es un problema distinto: se evita separando parámetros de la consulta mediante consultas preparadas cuando trabajes con bases de datos.

    Adjuntos: entender el recorrido antes de implementarlos¶

    Un formulario con archivos necesita enctype="multipart/form-data". PHP deja un temporal y describe nombre, tamaño, ruta temporal y error en $_FILES. Comprueba primero UPLOAD_ERR_OK, después los límites y el tipo real; accept en HTML solo ayuda a elegir, no valida en el servidor.

    La carpeta de destino y la política de ejecución son parte del diseño: un archivo recibido no debe convertirse accidentalmente en código ejecutable. El nombre del usuario no es un destino fiable. En este tema se explica el mecanismo; el laboratorio del telescopio no necesita adjuntos.

    UT2 · 4. Cookies, sesiones y acceso privado¶

    ¿Por qué una variable no recuerda la visita anterior?¶

    Cada petición ejecuta de nuevo el programa. Una variable como $seccion = 'mapas'; no recuerda una selección hecha en una petición anterior. HTTP no incorpora por sí mismo una memoria de usuario: la aplicación debe construirla.

    Mecanismo Dónde queda la información Ejemplo
    Variable normal Durante la ejecución de la petición Resultado de un cálculo
    Cookie En el navegador, que la envía en peticiones posteriores Preferencia de vista
    Sesión Habitualmente en el servidor; el navegador conserva el identificador Usuario autenticado

    El cliente puede modificar las cookies. No las uses como prueba de permisos. Una sesión también necesita controles de acceso en el servidor.

    Qué se pierde al terminar una petición¶

    Una variable normal existe durante la ejecución que la crea. Al pedir otra página, el servidor inicia otro procesamiento. Si necesitas recordar una preferencia o quién ha iniciado sesión, debes guardar ese estado mediante algún mecanismo apropiado.

    Esto no significa que el navegador olvide todo visualmente ni que se borren las tablas de una base de datos en cada visita. Significa que HTTP no relaciona por sí solo dos peticiones con un estado de aplicación que tú hayas definido.

    Una cookie permite al navegador conservar un dato y devolverlo en peticiones posteriores dentro de su ámbito. Una sesión utiliza normalmente una cookie identificadora para localizar información guardada en el servidor. Son mecanismos relacionados, no dos nombres para lo mismo.

    Qué ocurre al guardar una cookie¶

    setcookie añade una cabecera a la respuesta. Esa cabecera solicita al navegador guardar el dato. El navegador lo enviará después si la ruta, dominio y demás condiciones corresponden.

    Por eso $_COOKIE no contiene automáticamente el valor que acabas de enviar: representa lo recibido al comenzar esta petición. La nueva cookie todavía está viajando en sentido contrario. El ejemplo redirige para provocar un GET posterior y leer en él el dato actualizado.

    Al definir caducidad, piensa qué quieres recordar y durante cuánto tiempo. Al definir ruta, piensa qué páginas necesitan recibirla. Para una preferencia de vista basta un valor permitido, como lista o cuadricula; no necesitas guardar en la cookie todo el contenido del catálogo.

    Qué hace session_start¶

    Esta llamada crea o recupera la sesión correspondiente al identificador del cliente. Debe ejecutarse en cada página que vaya a utilizar ese estado y antes de enviar una salida que impida preparar las cabeceras necesarias.

    Después puedes escribir en $_SESSION y recuperar el valor en otra petición de la misma sesión. No basta con escribir una variable $usuario en una página y esperar que exista en las demás. Tampoco basta con mostrar un botón de entrada: la ruta privada necesita una comprobación en el servidor.

    Distingue el nombre de usuario del identificador de sesión. El navegador suele conservar el segundo; el servidor asocia con él la información necesaria. Compartir ordenador no obliga a compartir sesión, pero dos pestañas del mismo perfil normalmente comparten sus cookies.

    Entender el acceso por contraseña sin aprenderlo de memoria¶

    El formulario entrega un usuario y una clave. El servidor busca si conoce ese usuario y verifica la clave con el hash guardado. Si la comprobación funciona, renueva el identificador y conserva la identidad en la sesión. Después redirige a la zona privada.

    Un hash no es una clave cifrada que puedas recuperar con una operación inversa. password_verify utiliza la información del hash para comprobar una candidata. No compares el texto de dos llamadas nuevas a password_hash: pueden producir representaciones diferentes para la misma contraseña debido al uso de una sal aleatoria.

    Si la comprobación falla, el programa no debe crear una sesión autenticada por el simple hecho de que el campo usuario no esté vacío. Haber recibido un nombre no demuestra la identidad. El mensaje al usuario puede ser genérico para no revelar qué parte de las credenciales coincidió.

    Cómo comprobar entrada y salida¶

    Prueba primero abrir directamente la página privada sin entrar. Debe rechazarte o redirigirte. Prueba después una clave incorrecta y confirma que sigues sin acceso. Con la clave del laboratorio, entra y solicita de nuevo la página privada.

    Por último, sal y vuelve a pedir esa ruta. Destruir la sesión y eliminar su cookie no son exactamente la misma operación: el ejemplo contempla ambas. No te limites a pulsar «atrás», porque el navegador podría mostrar una representación ya almacenada sin que el servidor acabe de autorizarla otra vez.

    Problema explicado paso a paso: recordar la vista de un catálogo¶

    Guarda vista.php:

    <?php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $vista = $_POST['vista'] ?? '';
    if (is_string($vista) && in_array($vista, ['cuadricula', 'lista'], true)) {
        setcookie('vista_catalogo', $vista, [
            'expires' => time() + 86400 * 7,
            'path' => '/',
            'httponly' => true,
            'samesite' => 'Lax',
        ]);
        header('Location: vista.php', true, 303);
        exit;
    }
}
$vista = $_COOKIE['vista_catalogo'] ?? 'cuadricula';
if (!is_string($vista) || !in_array($vista, ['cuadricula', 'lista'], true)) {
    $vista = 'cuadricula';
}
?>
<p>Vista: <?= htmlspecialchars($vista, ENT_QUOTES, 'UTF-8') ?></p>
<form method="post" action="vista.php">
    <button name="vista" value="cuadricula">Cuadrícula</button>
    <button name="vista" value="lista">Lista</button>
</form>

    Seguimiento: la primera visita muestra cuadrícula. El botón envía POST; PHP envía Set-Cookie y una redirección 303; el navegador hace un nuevo GET con la cookie y muestra lista. $_COOKIE no se actualiza automáticamente con el valor que acabas de enviar: se lee de la petición recibida. En HTTPS añade 'secure' => true a las opciones de la cookie.

    setcookie, session_start y header deben ir antes de cualquier salida. Después de una redirección, exit detiene el programa. Es el patrón POST–Redirect–GET: recargar la página final repite el GET.

    Autenticación: comprobar quién entra¶

    La idea es formulario → verificar credenciales → renovar identificador → guardar identidad → comprobar identidad en cada ruta privada. Autorizar es decidir qué puede hacer esa identidad; autenticar y autorizar son decisiones diferentes.

    Minilaboratorio independiente de una biblioteca de partituras. Genera un hash con php -r 'echo password_hash("Partitura!47", PASSWORD_DEFAULT), PHP_EOL;'. Copia el resultado en un archivo local usuarios.php:

    <?php
return ['archivero' => 'PEGA_AQUI_EL_HASH_GENERADO'];

    acceso.php contiene el formulario y el procesamiento:

    <?php
session_start();
$usuarios = require __DIR__ . '/usuarios.php';
$error = '';
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $usuario = $_POST['usuario'] ?? '';
    $clave = $_POST['clave'] ?? '';
    if (is_string($usuario) && is_string($clave)
        && isset($usuarios[$usuario])
        && password_verify($clave, $usuarios[$usuario])) {
        session_regenerate_id(true);
        $_SESSION['identidad'] = $usuario;
        header('Location: archivo.php', true, 303);
        exit;
    }
    $error = 'No se ha podido validar el acceso.';
}
?>
<p><?= htmlspecialchars($error, ENT_QUOTES, 'UTF-8') ?></p>
<form action="acceso.php" method="post">
    <label>Usuario <input name="usuario" required></label>
    <label>Clave <input name="clave" type="password" required></label>
    <button>Entrar</button>
</form>

    archivo.php comprueba el acceso antes de enviar HTML:

    <?php
session_start();
if (!isset($_SESSION['identidad'])) {
    header('Location: acceso.php');
    exit;
}
?>
<h1>Archivo de partituras</h1>
<p>Identidad: <?= htmlspecialchars($_SESSION['identidad'], ENT_QUOTES, 'UTF-8') ?></p>
<form action="salir.php" method="post"><button>Salir</button></form>

    salir.php cierra la sesión:

    <?php
session_start();
if ($_SERVER['REQUEST_METHOD'] !== 'POST') {
    http_response_code(405);
    exit;
}
$_SESSION = [];
if (ini_get('session.use_cookies')) {
    $p = session_get_cookie_params();
    setcookie(session_name(), '', [
        'expires' => time() - 3600, 'path' => $p['path'],
        'domain' => $p['domain'], 'secure' => $p['secure'],
        'httponly' => $p['httponly'], 'samesite' => 'Lax',
    ]);
}
session_destroy();
header('Location: acceso.php', true, 303);
exit;

    Resultado esperado: el acceso directo a archivo.php redirige; las credenciales del laboratorio permiten entrar; después de salir, el acceso directo vuelve a redirigir. El hash es una representación para verificar la clave, no una clave cifrada que se descifra. Las credenciales mostradas son solo de prueba.

    Este ejemplo explica el mecanismo. Una aplicación publicada también necesita HTTPS, configuración segura de sesión, protección CSRF y controles contra intentos repetidos.

    Comprobar el aislamiento¶

    Entra en una ventana normal y abre archivo.php en una ventana privada: la segunda debe pedir acceso. Dos pestañas del mismo perfil suelen compartir cookies y sesión; no sirven para simular dos usuarios independientes.

    Reglas de sesión recuperadas y puestas en contexto¶

    Medida Qué aporta
    HttpOnly Impide leer la cookie mediante JavaScript; no elimina todos los efectos de XSS
    Secure Limita el envío de la cookie a conexiones HTTPS
    SameSite Restringe su envío en determinados contextos entre sitios
    Renovar el identificador al entrar Reduce el riesgo de fijación de sesión
    Caducidad por inactividad Limita cuánto dura un acceso abandonado

    Una política de inactividad se aplica comprobando la última actividad en el servidor, no solo ocultando una pantalla. Una cookie con admin=1 no prueba autorización; el servidor debe recuperar los permisos desde una fuente en la que confíe.

    Problema explicado paso a paso: entrar no significa tener cualquier permiso¶

    Imagina que el archivo de partituras distingue visitantes y personal de archivo. Después de verificar la identidad, la aplicación asigna un rol desde sus propios datos. Antes de una operación reservada, comprueba ese rol en el servidor.

    <?php
session_start();
if (($_SESSION['rol'] ?? '') !== 'archivo') {
    http_response_code(403);
    exit('Acceso no autorizado para esta operación');
}
echo 'Operación permitida al personal de archivo';

    En este fragmento no se fija el rol desde un formulario: presupone que el proceso de acceso lo ha guardado desde datos fiables. Sin sesión o con otro rol devuelve 403; con rol archivo, permite continuar. Es una comprobación de autorización, distinta del acceso por contraseña.

    El botón «atrás» puede mostrar una representación en caché después de salir. La prueba importante es solicitar de nuevo la ruta privada y comprobar que el servidor deniega el acceso. En contenido sensible puedes usar una política de caché como Cache-Control: no-store.

    1. Elige dónde recordar cada dato¶

    Para un visor de partituras debes guardar una preferencia de tamaño de letra y, por separado, la identidad del usuario que ha entrado. Explica qué dato podrías guardar como cookie de preferencia y cuál mantendrías en la sesión del servidor.

    Pista

    Una preferencia modificable no cumple el mismo papel que una identidad verificada.

    Solución paso a paso

    El tamaño puede guardarse como cookie, validando sus opciones al leerlo. La identidad verificada debe mantenerse como estado de sesión en el servidor.

    El navegador puede conservar un identificador de sesión. No utilizaría una cookie con el nombre escrito por el usuario como prueba de que ha iniciado sesión.

    2. Revisa dos navegadores¶

    Has iniciado sesión en un perfil y la zona privada funciona. En otro perfil limpio, la misma URL solicita acceso. ¿Es necesariamente un fallo? Explica la diferencia entre este caso y dos pestañas del primer perfil.

    Pista

    Solución paso a paso

    No es necesariamente un fallo: el perfil limpio no dispone de la cookie identificadora de la primera sesión.

    Dos pestañas del mismo perfil normalmente comparten cookies. Por eso no equivalen a dos usuarios independientes. Para comprobar aislamiento, los perfiles separados son una prueba más apropiada.

    3. Distingue entrar de tener permiso¶

    Un usuario ha iniciado sesión, pero solo el rol editor puede modificar una ficha. Escribe el control PHP de esa operación suponiendo que $_SESSION['rol'] se asignó desde datos fiables durante el acceso. Devuelve 403 si no corresponde.

    Pista

    Una identidad válida no concede todos los permisos.

    Solución paso a paso 
    <?php
session_start();
if (($_SESSION['rol'] ?? '') !== 'editor') {
    http_response_code(403);
    exit('No puedes modificar esta ficha');
}
echo 'Puedes continuar con la modificación';

    La comparación se hace antes de modificar nada. Un rol ausente también se rechaza. No se toma el permiso de un campo editable del formulario.

    UT2 · 5. Depurar una aplicación sin probar al azar¶

    Sigue el recorrido de la petición¶

    Cuando una página no hace lo que esperas, separa tres preguntas: ¿ha llegado la petición?, ¿qué ha recibido PHP? y ¿qué respuesta ha generado?. Un formulario que no conserva un valor no se diagnostica igual que un contenedor que no arranca.

    Empezar por una pregunta concreta¶

    «La web no funciona» incluye demasiados problemas posibles. Convierte esa frase en una observación: no conecta, recibe un estado inesperado, falta un campo, aparece una excepción o el cálculo es incorrecto. Cada observación orienta hacia una comprobación distinta.

    Anota también lo que esperabas. Si el formulario debía aceptar 15 minutos y muestra un error de rango, tienes una condición concreta que investigar. Si no sabes qué resultado esperabas, todavía no puedes decidir si el programa falla.

    Comprobar una capa cada vez¶

    Empieza por el acceso al servidor: URL y puerto correctos, servicio levantado y respuesta recibida. Después mira el procesamiento PHP: archivo ejecutado, método y campos. Finalmente comprueba el significado del resultado: reglas y cálculo.

    Esto evita cambiar la lógica de un formulario cuando todavía estás conectando al puerto equivocado. También evita reinstalar contenedores cuando el dato llega bien y el único fallo es leer una clave con otro nombre.

    El navegador permite observar la petición y la respuesta. Los logs permiten observar lo que ocurrió en el servicio. Una impresión temporal como var_dump permite observar una variable en un punto. Cada herramienta responde a una pregunta distinta; elige la que te permita comprobar tu hipótesis.

    Una hipótesis debe poder ponerse a prueba¶

    Si piensas «el campo no llega», abre el cuerpo del POST y búscalo. Si aparece, esa hipótesis ya no explica el problema. Mira después cómo lo lee el receptor. Si piensas «la sesión cambia en cada visita», observa la cookie y revisa si estás alternando perfiles.

    Cambiar muchas cosas antes de comprobar impide saber cuál influía. Haz una corrección pequeña, repite la entrada que fallaba y comprueba después que el caso que antes funcionaba sigue funcionando.

    No elimines una validación solo para obtener una pantalla de éxito. Puede que el dato enviado sea incorrecto y la validación esté haciendo bien su trabajo. La corrección debe respetar la regla que hayas definido para el problema.

    Leer un error de sintaxis con calma¶

    Un mensaje puede señalar la línea donde el intérprete ya no pudo continuar, no necesariamente la primera línea que contiene la causa. Si falta una comilla o un punto y coma antes, el problema puede hacerse visible al llegar a la siguiente instrucción.

    php -l archivo.php comprueba sintaxis sin atender una petición web completa. Que esa comprobación pase no demuestra que el formulario reciba sus datos ni que la sesión esté bien configurada. Después necesitas probar el comportamiento real.

    Guardar lo aprendido para la siguiente vez¶

    Anota síntoma, causa y corrección. «POST vacío → el control no tenía name → añadir el nombre y leer esa clave» es una referencia útil. «Reinicié y funcionó» no permite explicar la causa ni repetir con seguridad la solución.

    Este registro convierte los errores en material de estudio. Durante un ejercicio puedes reconocer un patrón sin repetir pruebas a ciegas, y en el examen puedes justificar qué comprobación harías primero y por qué.

    Problema explicado paso a paso: no aparece la duración del turno¶

    En un formulario de visita guiada el control dice name="duracion", pero el receptor lee $_POST['tiempo']. Al enviar 25, el resumen aparece vacío.

    1. En Red del navegador, abre la petición POST. El cuerpo contiene duracion=25: el navegador envía bien el dato.
    2. En desarrollo local, inspecciona el receptor con var_dump($_POST);. La clave es duracion, no tiempo.
    3. Corrige la lectura a $_POST['duracion'] ?? '' y valida el resultado antes de calcular.
    4. Vuelve a probar 25, un campo ausente y un texto no numérico.
    5. Retira la impresión de depuración. Si la dejas antes de un header(), puede impedir la redirección.

    Conclusión del caso: el problema era el acuerdo entre el nombre del campo y la clave que esperaba PHP. Añadir CSS, reiniciar MariaDB o cambiar de navegador no corrige ese desacuerdo.

    Una comprobación útil antes de dar por terminado un tema¶

    En Git, registra una corrección coherente con git add archivo.php, git diff --cached y git commit -m "Valida la duración del turno". El commit documenta el cambio; no sustituye la prueba de funcionamiento.

    Preparar una prueba que otra persona pueda repetir¶

    Anota el archivo que se ejecuta, el comando o URL, los datos exactos y el resultado esperado. Una captura sin esos datos puede mostrar un resultado, pero no explicar cómo reproducirlo.

    Para una validación de duraciones, separa los casos de forma (muchos), rango (4 o 41) y estructura (un array cuando esperabas texto). Si solo pruebas números dentro del rango, no detectas los otros problemas.

    En la salida de docker compose logs, identifica qué servicio escribe el mensaje. Un fallo DNS al conectar con MariaDB, una credencial rechazada y una tabla ausente requieren correcciones diferentes, aunque todos puedan terminar en una página de error.

    return "Hola, " . $nombre;
}
echo saludar("Ana");
    function define código reutilizable; $nombre es el parámetro; return devuelve el resultado; la llamada pasa "Ana" como argumento.

    Formularios¶

    Ejercicio 1 · Recibir GET¶

    <?php
$busqueda = $_GET['q'] ?? '';
echo htmlspecialchars($busqueda);
    $_GET contiene parámetros de la URL; ?? '' usa cadena vacía si q no existe; htmlspecialchars() escapa caracteres especiales antes de mostrarlos en HTML.

    Ejercicio 2 · Recibir POST¶

    <?php
$nombre = trim($_POST['nombre'] ?? '');
if ($nombre === '') {
    echo "El nombre es obligatorio";
}
    $_POST recibe datos enviados por POST; trim() elimina espacios exteriores; === compara valor y tipo; la validación evita aceptar una cadena vacía.

    Ejercicio 3 · Validar entero¶

    <?php
$edad = filter_input(INPUT_POST, 'edad', FILTER_VALIDATE_INT);
if ($edad === false) {
    echo "Edad no válida";
}
    filter_input() lee y valida. FILTER_VALIDATE_INT exige un entero; false indica que la validación no ha pasado.

    Estado: sesiones y cookies¶

    Ejercicio 1 · Sesión¶

    <?php
session_start();
$_SESSION['usuario'] = 'ana';
echo $_SESSION['usuario'];
    session_start() inicia o recupera la sesión antes de usar $_SESSION. El dato se asocia a la sesión del usuario entre peticiones.

    Ejercicio 2 · Contador de sesión¶

    <?php
session_start();
$_SESSION['visitas'] = ($_SESSION['visitas'] ?? 0) + 1;
echo $_SESSION['visitas'];
    Si no existe visitas, ?? 0 parte de cero. Después se suma uno y se guarda otra vez en la sesión.

    Ejercicio 3 · Cookie¶

    <?php
setcookie('tema', 'oscuro', time() + 3600, '/');
    setcookie() prepara una cabecera HTTP: nombre, valor, caducidad y ruta. Debe ejecutarse antes de enviar contenido de la respuesta.

    Depuración y errores¶

    Ejercicio 1 · Inspeccionar una variable¶

    <?php
$datos = ['nginx', 'php', 'mariadb'];
var_dump($datos);
    var_dump() muestra tipo, tamaño y contenido. Es útil durante la depuración, pero no debería dejarse como salida de una aplicación terminada.

    Ejercicio 2 · Registrar información¶

    <?php
error_log('Inicio del procesamiento');
    error_log() envía el mensaje al registro configurado en PHP. Permite investigar sin mostrar detalles internos al usuario final.

    Ejercicio 3 · Comprobar un dato antes de usarlo¶

    <?php
$id = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);
if ($id === false || $id === null) {
    exit('ID no válido');
}
echo "ID: " . $id;
    Primero se obtiene y valida la entrada; después se comprueban los casos inválidos; exit() detiene la ejecución y solo si todo es correcto se usa el dato.

    Método

    En PHP sigue siempre el recorrido entrada → validación → proceso → salida. En formularios y estado, indica además de dónde procede cada dato ($_GET, $_POST, $_SESSION o cookie).
